Vega + Sharpa vs YAM Deployment

How a camera frame and a joint vector travel from the robot to the model and back, for the YAM arms and for the new vega robot (Tianji arms + Sharpa hands). Both robots use the same server and model. They differ in five places, all chosen by one flag.

Start here

  • One switch. --embodiment sharpa (or EMBODIMENT=sharpa for deploy/launch_server.sh) turns on everything Sharpa-specific. The default, yam, runs exactly as before. The server never guesses the robot from the task name.
  • Most of the path is shared. The HTTP server, request validation, JPEG/PNG decoding, the model call and the response format are the same files for both robots.
  • Five things differ: the state size the robot sends (14 vs 58), the camera size and crop, a strict resolution check (Sharpa only), the kinematics library used for FK/IK, and how a predicted chunk is turned back into joints.
  • Where to start debugging: read the error text first. Startup errors come from PolicyRuntime.__init__; per-request errors come back as HTTP 400 with the field name; silent bad motion is almost always a state-layout or kinematics problem (see Symptom → cause).

Startup: who calls whom

What runs once when you start the server. Every red line is a check that stops startup with a message; search the log for that text.

  • deploy/launch_server.shshared
    Needs CKPT, DATASET, INSTR, AGENTICWAM_DEPLOY_TOKEN. Turns EMBODIMENT into --embodiment and INFER_CODE_TOKENS into model.infer_code_tokens.
    • deploy/remote/server.pymain()shared
      Parses flags, builds PolicyRuntime, runs the warmup, then serves /ping, /health, /act, /reset on port 8712.
      • deploy/common/policy_runtime.pyPolicyRuntime.__init__()shared
        Composes the task config, then looks up _EMBODIMENTS[embodiment] (line 41) to pick the transform, bridge, client dimension and image step.
        Stops if: the embodiment name is unknown; sharpa is given a checkpoint whose model.action_dim is not 64; the task's transform does not end in the required name.
        • deploy/common/yam_eef64.pyyam
          Imported by name through importlib. Loads utils/yam_fk_ik/yam_kinematics.py, which builds the MuJoCo model from station/station/station.xml.
        • deploy/common/vega_eef64.pysharpa
          Imports TianjiSharpaUnifiedEEFTransform from src/agenticwam/datasets/lerobot/transforms/tianji_sharpa_unified_eef.py and utils/vega_fk_ik/vega_kinematics.py, which loads urdf/vega_1.urdf with Pinocchio.
          Stops if pinocchio is missing (ImportError at import time). pink, qpsolvers and daqp are imported on the first IK call instead, so a missing one shows up during warmup.
        • policy_runtime.pyparity_crop checksharpa
          Stops if AGENTICWAM_EVAL_PREPROC=parity_crop: it would crop the already-cropped Sharpa frame again.
        • deploy/common/resolution_guard.pysharpa_guard()sharpa
          Creates the per-camera 360×640×3 check used on every request.
        • robotwin/deploy/deploy_policy.pyAgenticWAMCosmosRobotWinPolicy(...)shared
          Loads the checkpoint, VAE, text encoder and dataset stats. A missing CKPT path gives SMOKE MODE: shapes flow but actions are meaningless.
      • policy_runtime.pyPolicyRuntime.warmup()shared
        One fake inference with black frames: 480×640 for YAM, 360×640 for Sharpa. This exercises the whole /act path, IK included, so a broken FK/IK install fails here, before the robot is connected. The resolution check's counters are reset afterwards.

def state58_to_raw76(state58):
    s = np.asarray(state58, np.float64).reshape(-1)
    assert s.shape == (58,)
    T_L, T_R = vk.fk_both(s[L_ARM], s[R_ARM])  # 0:7, 29:36
    raw76 = np.zeros(76, np.float64)
    raw76[0:16] = T_L.reshape(-1)
    raw76[16:32] = T_R.reshape(-1)
    raw76[32:54] = s[L_HAND]   # 7:29
    raw76[54:76] = s[R_HAND]   # 36:58
    return raw76
  • Both write the two 4×4 EEF poses into slots 0–31 in the same order (left, right). After that the layouts differ: YAM appends grippers and joints, Sharpa appends the two hands.
  • If the robot sends its 58 values in a different order (for example both arms first, then both hands), nothing fails: FK runs on hand values and the arms move wrongly. Check the order first when motion looks wrong.

def head_camera_view(frame):
    assert frame.shape == RAW_SHAPE
    y0, y1, x0, x1 = HEAD_CROP
    cropped = frame[y0:y1, x0:x1]
    return cv2.resize(cropped, (MODEL_W, MODEL_H),

def wrist_camera_view(frame):
    assert frame.shape == RAW_SHAPE
    return cv2.resize(frame, (MODEL_W, MODEL_H),
                      interpolation=cv2.INTER_AREA)

def decode_chunk(delta64, state14):

                          "left", init6=qL)

                          "right", init6=qR)
        failures += (not ok_l) + (not ok_r)
        out[t, 0:6] = qL
        out[t, 6] = d[t, L_GRIP]
        out[t, 7:13] = qR
        out[t, 13] = d[t, R_GRIP]
    return out, failures

def decode_chunk(delta64, state58):
    raw76 = state58_to_raw76(s)
    state64 = _TRANSFORM._state64(raw76 …)
    abs64 = _TRANSFORM.backward(batch)["action"]["default"][0]
    qL, qR = s[L_ARM].copy(), s[R_ARM].copy()  # IK seed
    out = np.zeros((d.shape[0], 58))
    for t in range(d.shape[0]):
        T_L = _pose_from_abs9(abs64[t, L_EEF9])
        T_R = _pose_from_abs9(abs64[t, R_EEF9])
        ok, qL, qR = vk.ik_both(T_L, T_R, qL, qR)
        failures += int(not ok)
        out[t, L_ARM] = qL
        out[t, L_HAND] = abs64[t, L_HAND64]
        out[t, R_ARM] = qR
        out[t, R_HAND] = abs64[t, R_HAND64]
    return out, failures
  • Both anchor every row to the chunk-start pose and seed IK with the previous row, so IK follows the trajectory.
  • YAM rebuilds the absolute pose with its own apply_delta_9d. Sharpa calls the training transform's backward, so the delta convention cannot drift from training.
  • YAM counts a failure per arm (up to 2 per row). Sharpa counts one per row, because both arms are solved together.

IK solver

def ik(T_target, arm="left", init6=None,
       iters=100, damp=1e-4):
    # MuJoCo damped least squares, one arm, 6 DOF
    for _ in range(iters):
        mujoco.mj_kinematics(_m, _d)
        ...
        if norm(ep) < 1e-4 and norm(er) < 1e-3:
            break
        dq = J.T @ solve(J @ J.T + damp * I, err)
        _d.qpos[q] += np.clip(dq, -0.3, 0.3)
    return norm(ep) < 1e-3, _d.qpos[q].copy()

def ik_both(T_L, T_R, initL7, initR7,
            iters=5, dt=0.05):
    # Pink differential IK, both arms, 7 DOF each
    left_task  = FrameTask("L_ee", position_cost=50.0, ...)
    right_task = FrameTask("R_ee", position_cost=50.0, ...)
    smoothness.set_target(initial_qpos)
    regularization.set_target(_arms.default_qpos)  # home pose
    for _ in range(iters):
        v = _pink_solve_ik(..., solver="daqp")
        configuration.integrate_inplace(v, dt)
        # clip to joint limits
    pos_err = max(|T_L_actual - T_L|, |T_R_actual - T_R|)
    return pos_err < 1e-3, qL7, qR7
  • The vega arms have 7 joints for a 6-D target, so many joint solutions reach the same pose. The home-pose target (LEFT_ARM_HOME / RIGHT_ARM_HOME from the T-Rex teleop config) picks one. A wrong home pose gives odd elbow positions without any error.
  • 5 iterations is the teleop setting, which assumes small steps between targets. A large jump between rows can leave the position error above 1 mm and raise ik_failures.

Known gaps

  • Real FK/IK not run yet. Pinocchio and Pink weren't installed on the machine where the bridge was tested, so the tests used stub kinematics. Run check 1 first.
  • No vega robot client. deploy/robot/agenticwam_client.py only speaks 14-D YAM. The station side needs a client that sends 640×360 frames and the 58-D state in the order above.
  • No recorded-episode test for the Sharpa bridge. YAM has validate_yam_eef64.py. A Sharpa version would replay one converted episode through state58_to_raw76 and decode_chunk and compare with the recorded joints.
  • RTC is ignored for Sharpa. committed and freeze in the request are not used.
  • Grayscale and RGBA don't reach the resolution check. obs_codec converts every image to RGB first, so the channel messages in resolution_guard.diagnose only appear when PolicyRuntime is called directly.
  • Older server stays YAM-only. deploy/deploy_server.py has no --embodiment flag. Use deploy/remote/server.py through deploy/launch_server.sh.
